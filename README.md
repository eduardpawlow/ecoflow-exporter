# EcoFlow exporter

Минимальный MQTT → Prometheus экспортер для Raspberry Pi 5 с 64-битной Linux.
Основан на [vbash/ecoflow_exporter](https://github.com/vbash/ecoflow_exporter),
исходный коммит `9a32d1359919ddfac270002ce9f6dae8abab9068`. Лицензия исходного проекта GPL-3.0 сохранена в LICENSE.

## Запуск

Сначала разместите содержимое этого каталога в ветке `master` репозитория
`eduardpawlow/ecoflow-exporter`. Если используете `main`, замените `#master`
на `#main` в compose.yaml. Удалённый build context должен быть доступен серверу.

На Raspberry Pi нужны Docker Engine и Docker Compose v2.
Скопируйте compose.yaml и .env.example в каталог сервиса:

```bash
cp .env.example .env
chmod 600 .env
nano .env
docker compose up -d --build
docker compose logs --tail=100 -f ecoflow-exporter
curl -fsS http://127.0.0.1:19094/metrics
```

В `.env` заполните DEVICE_SN, ECOFLOW_USERNAME и ECOFLOW_PASSWORD.
Пароль можно заключить в одинарные кавычки, чтобы `$` не интерполировался.
`.env` исключён из Git и Docker context.

Compose собирает **удалённую ветку**, поэтому локальные правки не попадут в сборку
до отправки в GitHub. Для сборки до публикации временно замените `build.context`
на `.` и запускайте Compose из этого каталога.

Метрики доступны только на самом хосте: `127.0.0.1:19094/metrics`.
Prometheus в отдельном контейнере не сможет обратиться к ним через собственный localhost.
Метрики устройства появляются после получения MQTT-сообщений.

## Состав и изменения

Один Python-файл, Dockerfile, закреплённые зависимости, Compose и пример окружения.
Включён JSON дашборда Smart Home Panel; дополнительные сервисы Grafana/Prometheus, изображения и CI не включены.
Все runtime-зависимости, включая транзитивные, закреплены через `==`.
`paho-mqtt==2.1.0`: клиент и callbacks переведены на Callback API VERSION2.
Версии всех runtime-зависимостей проверены по PyPI 2026-09-13.
Базовый Python 3.12 Alpine закреплён digest многоархитектурного образа с ARM64.
Все пакеты устанавливаются из готовых wheels (`--only-binary=:all:`);
setuptools, wheel и packaging для сборки больше не нужны.

В коде убраны неиспользуемый импорт и закомментированные фрагменты,
добавлен таймаут HTTP 30 секунд, явный client_id и обработка отсутствующего params
и некорректного имени метрики. Имена метрик для дашборда сохранены; у глубоко вложенных объектов теперь сохраняется полный путь ключа.
`ecoflow_online` означает наличие сообщений за интервал обработки (по умолчанию 10 секунд),
а не независимую проверку доступности устройства.

Опциональные переменные: DEVICE_NAME (по умолчанию DEVICE_SN), LOG_LEVEL (INFO),
COLLECTING_INTERVAL (10 секунд), EXPORTER_PORT (9090).

Проверки подготовки: установка закреплённых зависимостей, создание MQTT-клиента,
обработка тестового payload и выдача метрик HTTP. Реальное подключение к EcoFlow
и сборка контейнера ARM64 требуют проверки на устройстве.

## Дашборд Grafana: EcoFlow Smart Home Panel

Файл [GrafanaEcoflowSmartHomePanel.json](GrafanaEcoflowSmartHomePanel.json) основан
на дашборде исходного репозитория. Он содержит 22 панели для Smart Home Panel,
10 электрических цепей и двух подключённых DELTA Pro:

- заряд резервных батарей, температура, оценка времени работы и зарядки;
- состояние электросети, системы и каждой DELTA Pro;
- суточное потребление от сети и резервного питания;
- суммарная мощность, мощность по цепям и доли потребления;
- входная/выходная мощность DELTA Pro и история отключений сети.

Дашборд ожидает метрики Smart Home Panel (`ecoflow_backup_*`, `ecoflow_grid_*`,
`ecoflow_energy_infos_*`, `ecoflow_info_list_ch_watt_*`, `ecoflow_state_bean_*`).
Для других моделей набор метрик может отличаться: отсутствующие данные дают пустые панели.
Значения и единицы измерения в запросах сохранены из исходного дашборда.
JSON экспортирован из Grafana 9.4.3 (schemaVersion 38); совместимость с установленной
версией Grafana нужно проверить при импорте.

### Подключение

1. Настройте сбор `/metrics` в существующем Prometheus. Если Prometheus работает
   непосредственно на том же хосте или использует host networking, подходит такой job:

   ```yaml
   scrape_configs:
     - job_name: ecoflow
       scrape_interval: 10s
       static_configs:
         - targets: ["127.0.0.1:19094"]
   ```

   Добавьте job в существующий `scrape_configs`. Для Prometheus в обычной Docker-сети
   localhost указывает на его собственный контейнер; потребуется отдельно настроить
   доступ к экспортеру через общую сеть или адрес хоста.
2. Добавьте Prometheus как источник данных в Grafana.
3. Импортируйте `GrafanaEcoflowSmartHomePanel.json` через функцию импорта дашборда
   и выберите этот источник данных для входного параметра `DS_PROMETHEUS`.
4. В поле `Device ID` укажите значение метки `device`: обычно это `DEVICE_SN`,
   а при заданном `DEVICE_NAME` — именно `DEVICE_NAME`. Задайте названия `Circuit 1`–`Circuit 10`.

Исходный серийный номер и названия домашних цепей заменены нейтральными значениями.
Запросы сохранены: большинство из них **не фильтруются по Device ID**.
Этот вариант рассчитан на один Smart Home Panel в источнике данных;
для нескольких устройств нужно добавить фильтр `{device="$deviceId"}` к соответствующим метрикам.

## Проверка кода

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Тесты работают без аккаунта EcoFlow: проверяют MQTT callbacks v2, повторную подписку,
обработку некорректных сообщений, вложенных метрик и HTTP `/metrics`.
Нечисловые и бесконечные значения пропускаются; некорректные имена и коллизии
метрик не останавливают обработчик. HTTP-ошибки авторизации не выводят тело ответа с токенами.
Переподключение MQTT использует задержку 1–60 секунд без блокировки callbacks.
Реальное подключение к EcoFlow и ARM64-контейнер проверяются отдельно на устройстве.

## DELTA 3 Plus: бинарная телеметрия

Compose по умолчанию задаёт DEVICE_MODEL=delta3_plus. Для старых JSON-устройств задайте DEVICE_MODEL=json.
Поддержаны DisplayPropertyUpload (254/21), RuntimePropertyUpload (254/22),
BMSHeartBeatReport (32/50), CMSHeartBeatReport (32/2), включая XOR по seq.
Неизвестные команды не интерпретируются как метрики. Отсутствующие поля не заменяются нулями.

Примеры метрик: ecoflow_display_pow_in_sum_w, ecoflow_display_pow_out_sum_w,
ecoflow_bms_0_f32_show_soc, ecoflow_bms_0_cycles, ecoflow_bms_0_temp,
ecoflow_bms_0_vol (мВ), ecoflow_bms_0_amp (мА). Префиксы display/runtime/cms
разделяют типы сообщений; bms_0, bms_1 разделяют батареи. Единицы исходных полей сохранены.

OFFLINE_TIMEOUT=120 задаёт время сохранения данных после последней распознанной телеметрии.
Устройство присылает частичные обновления: внутри этого окна сохраняются предыдущие значения полей.
Экспортер только подписывается на MQTT, не отправляет команды управления или опроса.

Для DELTA 3 Plus используйте GrafanaEcoflowDelta3Plus.json.
GrafanaEcoflowSmartHomePanel.json оставлен для Smart Home Panel.

Схема delta3.proto и сгенерированный delta3_pb2.py включены в репозиторий.
Runtime-зависимость protobuf==7.36.1 закреплена; grpcio-tools не нужен в контейнере.
Для регенерации схемы в отдельной среде установите grpcio-tools==1.83.1 и выполните:

    python -m grpc_tools.protoc -I. --python_out=. delta3.proto

Источник схемы и лицензия указаны в THIRD_PARTY_NOTICES.md. Проверка на 10 реальных
пакетах DELTA 3 Plus подтвердила декодирование всех полученных сообщений;
RuntimePropertyUpload отдельно проверяется синтетическим тестом.

## Дашборд DELTA 3 Plus

Импортируйте [GrafanaEcoflowDelta3Plus.json](GrafanaEcoflowDelta3Plus.json) в Grafana,
выберите Prometheus и устройство из списка. Все запросы фильтруются по метке `device`.
Если список пуст, проверьте сбор `ecoflow_online` в Prometheus.

20 панелей: заряд, мощность станции/AC/батареи, температура, циклы, напряжение и ток,
лимиты SOC, температуры ячеек и MOS, напряжения 16 ячеек, ёмкость, коды BMS и MQTT.
Дашборд показывает основную батарею `bms_0`. Дополнительные батареи не суммируются с ней.
В и А получаются из мВ и мА делением на 1000; ёмкость показывается в А·ч.
Для AC входа/выхода показан модуль мощности; ток батареи сохраняет знак.
Нет данных означает отсутствие метрики, а не нулевое значение.

Окно по умолчанию — 6 часов, обновление — 10 секунд. Метрика online оценивает свежесть
распознанной телеметрии; при превышении OFFLINE_TIMEOUT накопленные поля очищаются.
Пакеты являются частичными обновлениями, поэтому отдельные поля могут обновляться реже.
Проверены JSON, расположение панелей, фильтры устройства и наличие используемых
метрик в записанной телеметрии; импорт и внешний вид в работающей Grafana требуют проверки.

## Эксперимент: MQTT-keepalive через запрос latestQuotas (ветка feature/mqtt-quota-keepalive)

У части пользователей EcoFlow (в том числе в issue-трекерах `ecoflow_exporter` и
`hassio-ecoflow-cloud`) телеметрия по MQTT перестаёт идти, если закрыто мобильное
приложение EcoFlow, хотя соединение экспортера с брокером остаётся живым. Причина —
на стороне облака EcoFlow, повлиять на неё нельзя; это не баг данного экспортера.

`QUOTA_REQUEST_INTERVAL` (секунды, по умолчанию `0` — выключено) включает
периодический запрос полного снапшота параметров через тот же приватный API,
которым пользуется приложение: раз в заданный интервал экспортер публикует

```json
{"version": "1.1", "moduleType": 0, "operateType": "latestQuotas", "params": {}}
```

в топик `/app/{user_id}/{device_sn}/thing/property/get` и подписывается на
`/app/{user_id}/{device_sn}/thing/property/get_reply`, где устройство должно прислать
ответ. `user_id` берётся из ответа логина автоматически. Ответ на `get_reply` приходит
в общую очередь сообщений и обрабатывается тем же кодом, что и обычные JSON-сообщения
(отдельного парсера не требуется).

**Это не гарантированный фикс.** Механизм подсмотрен в `hassio-ecoflow-cloud`
(`quota_all()` / `get_quota_message()`), но там та же самая проблема "работает только
при открытом приложении" всё ещё воспроизводится с этим механизмом включённым — то
есть периодический get-запрос помогает не всем и не всегда. Это дешёвый безопасный
эксперимент (запрос только на чтение), а не подтверждённое решение.

Как проверить:

```bash
# в .env
QUOTA_REQUEST_INTERVAL=30
```

Пересобери и смотри лог: должны появляться `Requested quota snapshot on
/app/.../thing/property/get` каждые 30 секунд и, если устройство ответило,
`Created new metric from payload key ...`. Проверяй именно при закрытом приложении
EcoFlow — если поток метрик продолжается там, где раньше останавливался, эксперимент
удался.

Эта ветка использует тот же удалённый git-контекст сборки (`#master` в `compose.yaml`).
Чтобы собрать именно ветку `feature/mqtt-quota-keepalive` на Raspberry Pi, временно
замени `#master` на `#feature/mqtt-quota-keepalive` в своей копии `compose.yaml`
(после `git push` этой ветки), либо собери локально с `build.context: .` как описано
выше в разделе «Запуск».
